## Decision

1. *Anchoring.* The egress ledger produces a checkpoint every `checkpoint_every` entries or `checkpoint_interval` minutes, whichever first. A checkpoint is the chain digest at that sequence; a separate signer (OPS-002) signs it and ships it to an append-only anchor sink outside the host (the gateway's telemetry path under Q7, or an object store with object lock). The sink acknowledges with a receipt that is appended to the egress ledger. The verifier tool checks chain, signatures and receipts and reports the last anchored sequence.
2. *Anchor unavailable.* Checkpoints queue locally with a bounded backlog; the ledger keeps appending (availability of egress records is never sacrificed to anchoring). Beyond the backlog bound, the window is marked `unanchored` and the EVL-009 blocker opens; the proxy keeps running. Nothing about the anchor ever changes a gate decision.
3. *Rollback.* Every deployable change (proxy version, config version, inventory version, artifact version) has a recorded previous version and a one-step rollback command; D4 requires the rollback to have been exercised in the pilot (EVL-007). Rollback never releases a pin and never rewrites ledger history.
4. *Incident response.* Runbooks exist for: chain verification failure (treat the ledger as untrusted from the last verified checkpoint, preserve the file, open a security incident); served identity outside the inventory (OPS-003 mismatch: freeze routing to `off` with gates enforced, notify the gateway team); key compromise (OPS-002: rotate, re-sign the inventory, re-anchor); pinned lineage reached a cloud rung (SAF-004 breach: freeze, audit query, disclosure per policy); fail-open rate alert (OPS-008). Each runbook names the first responder, the freeze action and the evidence to preserve.

## Context and rationale

SAF-009 promises tamper-evidence and the review's Q5 answer promises that "did this code ever leave the machine" is a ledger query. Neither holds without an anchor outside the host, since a host-local chain can be regenerated by whoever holds the host. The 2026-09-03 external review found the anchor absent and the CLI verifying only the chain. This decision specifies the anchoring loop, what happens when it fails, and the runbooks the SAF decisions imply but never wrote.

## Adversarial review (2026-09-03)

### Steelman
Periodic signed checkpoints shipped to an append-only sink is the standard transparency-log shape; the design cost is small and the property it buys, that deletion or edit is detectable by someone who does not trust the host, is the whole value of SAF-009.

### Attacks
1. **An unreachable sink for a long time makes the whole window unanchored.** Answered: correct, and visible; the blocker is the honest state. The backlog bound is pre-registered.
2. **Runbooks rot.** Answered: each runbook is exercised at least once before D4 (rollback) and reviewed at every graduation meeting; the scorecard lists the last exercise date.
3. **Freezing routing to `off` on a mismatch is itself a denial of service.** Answered: `off` forwards to the harness-requested model with gates enforced; the developer keeps working, only routing stops.

### Evidence
- ADRL-SAF-009 (Proposed); hash chain, periodic signed checkpoints shipped off-device, verifier tool, audit query.
- ADRL-SAF-004 (amended); a pinned lineage cannot reach any cloud rung by any actor; the breach this runbook handles.
- ADRL-FND-004 (replacement); operator bypass audited with actor and reason; fail-open alerting.
- 2026-09-03 external review of adrl-core, finding P0-3; manual checkpoints only; CLI ignores signatures.

### Verdict
**PROPOSED.** The operational half of SAF-009 and SAF-004. Needs security and the gateway team as owners; the sink choice is a Q7 decision.
