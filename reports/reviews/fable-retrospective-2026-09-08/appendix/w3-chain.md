Inspector: rv-w3 (Claude Fable 5.1). Read-only on both repositories. All observations come from the frozen snapshot under `adrl-review-fable-2026-09-08/snapshot/` and from a disposable copy of the runtime at `adrl-review-fable-2026-09-08/disposable-w3/`. Author statements were treated as hypotheses and checked against code, tests, evidence JSON and hashes.

## 1. Summary

The W3 chain is a set of narrow, honestly labelled internal primitives. Every slice's code exists in the frozen runtime, every test module has the test count the reports claim, and the evidence chain from W0 through the transport-receipts slice is hash-consistent with the snapshot apart from three files changed later by the W7.0a routing correction. Nothing in the chain can attribute a real task's output: attribution is the literal `unestablished` on every journal event, `exact_close_eligible` is a `Literal[False]` on every process, coordination, resource and launch record, and there is no code anywhere in the runtime that extracts output from a stopped container. The `validated_pinned_synthetic_engine` state covers one self-authored fixture binary running one pinned command on one Docker engine, verified in a single combined run whose logs live outside the register. The eight skipped tests are the two opt-in Docker acceptance modules, skipped by policy since that run.

The next planned prerequisite, active-copy custody, is a real gap but it is not on the shortest credible path to a real-task demonstration. The isolated backend cannot host Claude Code at all: its policy pins the fixture command, forbids network and mounts, and has no image/credential profile. A narrower safe path exists through native observation plus the existing operator capture and snapshot verifier, provided attribution stays `operator_capture` and learning eligibility stays false. Section 5 spells out what that path still needs.

## 6. Minimal-path analysis

**The question.** Is active-copy custody plus exact-output qualification the minimum for a credible real-task demonstration with attributed outputs, or is there a narrower path that does not bypass the privacy or attribution gate?

**What "attributed" can mean today.** The register's own vocabulary has two levels. `operator_capture` is an encrypted, integrity-checked copy of a declared workspace at the moment a trusted local operator asks for it; it survives later edits and its manifest reference can be compared with the verifier's `source_snapshot_ref`. `exact_close` attribution requires a proven writer barrier at the close boundary and is set to `False` by schema in every W3 record. No slice, including the isolated backend, produces an exact-close record.

**Why the isolated backend is not on the path to a real Claude task.** The backend's `ExecutionPolicy` pins `fixture_argv` to `/probe forced_stop`, the image to one archive digest and the engine to one kernel string (`execution_control.py:14-50`). `ContainerControl.prepare` refuses any inherited image environment or entrypoint and sets `NetworkMode: none` with no mounts (`container_control.py:703-764`). Claude Code needs a network path to the gateway, credentials, and a repository checkout inside the container. Every one of those is a decision-queue item (image, network, credential and retention profile; DQ6 for copies). Therefore, even after active-copy custody and safe extraction are finished, a real-task exact-close demonstration still needs a new backend profile and a user decision. Active-copy custody is a prerequisite for real payload capture in general, but it is not the binding constraint on the first real demonstration.

**The narrower safe path.** The runtime already has, in production code paths that were exercised with a real Claude Code session on 2026-09-07:

1. Native observation through the product API with a signed workload assertion (`adrl launch`, live pilot report).
2. `adrl ledger verify-finish --auto-snapshot`, which refuses the live workspace, makes a detached git worktree snapshot and runs reviewed checks in the Seatbelt sandbox, recording `source_snapshot_ref` and `executed_snapshot_ref` (`src/adrl/cli/ledger_commands.py:169-210`, `session_verification.py:257-300`).
3. `CaptureArchive.capture` and `materialize` from W3.1, keyed by the same bound session.

A demonstration that runs one Claude Code task natively, then captures with `CaptureArchive` immediately at the operator's declared close, then runs the verifier against the materialized copy rather than a fresh worktree, would produce an output whose identity is fixed at capture time and whose receipt can name that capture. It bypasses no privacy gate: the capture reuses the bound session key, adds no key, and is erased with the session. It bypasses no attribution gate as long as the receipt says `operator_capture` and `eligible_for_learning` stays false, which the schema enforces. It does not need Docker, active-copy custody beyond what `materialize` already does on normal exit, or any engine allowance.

**What that path still needs, concretely.**

- A verifier entry point that accepts a capture ID and runs `SnapshotVerifier.evaluate` on the materialized directory, and a receipt field binding `capture_id` and the capture's `source_ref`. Today `evaluate` takes a workspace path and re-snapshots it; the capture is not consulted anywhere (`rg CaptureArchive src/adrl` finds only `attempts.py`).
- An attempt journal start before the task and a close request after it, so two attempts in one session stay distinct; both exist but nothing calls them from the CLI.
- A stated rule that an operator capture taken while Claude Code is still running is `incomplete`, not `operator_capture`, since no writer barrier exists natively. The double scan in `capture.py:225-229` rejects drift during the scan but cannot prove the harness had stopped.
- The existing DQ items that already applied to the 2026-09-07 pilot: subscription account use, a pinned CLI version, one approved task repository and the private evidence lifecycle. No new spend authority is required if the pilot's authorization still stands; I could not verify that from the repositories.
- Crash-leftover cleanup for `materialize` remains a documented gap; for a supervised one-off demonstration it is an operational risk, not a correctness bypass, and should be recorded as such rather than fixed first.

**Recommendation.** Reorder: build the capture-to-verifier binding and a `product capture` CLI first (a W3.3 element, small), run the bounded native demonstration with `operator_capture` attribution, and then return to active-copy custody as the prerequisite for the isolated backend and bulk collection. This produces attributed outputs sooner without relabelling anything as exact-close.

## 7. Findings

**F1. Isolated backend cannot host a real harness; the roadmap's next W3 step does not lead to a real-task demonstration.** Severity: high. Confidence: high. Files: `src/adrl/core/execution_control.py:14-50`, `src/adrl/core/container_control.py:703-764`, `reports/waves/w3-active-copy-custody.md`, `research/adrl-execution-state.json` `next_action`. Claim: "then a concrete real Claude Code profile/task/verifier matrix" follows custody work. Observation: argv, image layer, kernel and no-network are literal pins; a real harness needs a new backend profile behind decision-queue gates. Consequence: sequencing custody first delays the first attributed real-task evidence without shortening the gated work. Acceptance: a written ordering that names the first demonstration's attribution level (`operator_capture`) and the CLI/receipt fields it needs, before another custody slice starts.

**F2. Frozen wave packets were amended after their hashes were recorded.** Severity: medium. Confidence: high. Files: `research/adrl-w3-2b2d2-launch-contract-2026-09-08.json` `research_source_files`, `research/adrl-w3-execution-identity-2026-09-08.json`, `research/adrl-w3-isolated-launch-2026-09-08.json`; register `reports/waves/w3-2b2d2-launch-admission.md`, `w3-isolated-execution-contract-v1.md`, `w3-2b2d2-identity-compatibility.md`, `w3-isolated-launch-runtime.md`, `w3-launch-create-receipt-diagnosis.md`. Claim: packets are "frozen before" work. Observation: five packet hashes recorded in evidence no longer match the register; each file has appended "disposition" sections dated the same day. The frozen copies exist only in the private state directory. Consequence: the register cannot prove what the contract said at freeze time; a reader must trust that only appendices changed. Acceptance: for every packet named in a `research_source_files` block, either the frozen copy is added to the register under `research/<slice>/frozen/` or the evidence JSON records the amended hash alongside the frozen one.

**F3. Engine evidence is not independently checkable from the register.** Severity: medium. Confidence: high. Files: `research/adrl-w3-transport-receipts-2026-09-08.json` (`check_manifest`, `engine_stages[*].log`), `research/adrl-w3-isolated-launch-2026-09-08.json` (`engine_focused_runs`). Claim: 895 passed, zero skipped, 13 receipts and 13 absence confirmations. Observation: all logs, manifests and the receipts JSONL are under `~/projects/.adrl-execution-state`; the register carries counts and some sha256 values. The eight engine tests have been skipped in every later run. Consequence: the only claim that a real daemon lifecycle works rests on one un-reviewable run. Acceptance: publish the redacted `resources.jsonl` (IDs, events, timestamps) and the combined-run manifest into the register, or rerun the eight cases once under an observer with a fresh allowance and keep the log in the register.

**F4. No output extraction or capture association exists for stopped containers.** Severity: high for the product claim, low as an inconsistency. Confidence: high. Files: `src/adrl/core/isolated_execution.py:396-445`; `rg "archive|tarfile"` over `src/adrl` finds nothing. Claim (execution-identity report): "known startup plus sealing and a matching observed exit can retain the container layer as stopped". Observation: `stopped` is a daemon state observation; nothing reads `/work`; only the research driver ever read fixture output, in memory. Consequence: the "retained layer" is not evidence of any output. Acceptance: a test that reads the stopped fixture's `/work` file through the Engine archive endpoint under the same identity projection and stores its digest in the launch history.

**F5. Operator name-based cleanup contradicts the recorded product rule, documented as an exception.** Severity: low. Confidence: high. Files: `reports/waves/w3-launch-runtime-engine-acceptance.md` closed-batch section; `research/adrl-w3-isolated-launch-2026-09-08.json` `operator_candidate_review`. Claim: "no name-based adoption". Consequence: acceptable for a disposable fixture, but it shows that lost-receipt recovery in practice requires a human to break the rule. Acceptance: define, in the custody packet, a reviewed operator recovery procedure with its own audit event so the next occurrence is not an exception.

**F6. Permanent fences with no release make every supervised workspace single-use.** Severity: medium. Confidence: high. Files: `src/adrl/ledger/attempts.py:38-49`, `docs/attempt-coordination.md:31-36`, `resource_owner.py:367-381`. Claim: conservative by design. Observation: `check_execution_fence` blocks any new journal attempt on a fenced workspace forever, and a fence commits before any launch, including failed admissions. Consequence: no real repository can be supervised twice; a lost ledger acknowledgement fences a workspace with no process. Acceptance: a release contract (or an explicit decision that fences are per disposable copy only) before any real-repository supervision.

**F7. Unverified suite count in the frozen copy.** Severity: low (outside W3). Confidence: medium. Files: `disposable-w3/full-suite.log`, `tests/unit/test_routing_lab.py:61`. Claim: 911 passed, 8 skipped. Observation: my full run gave 906 passed, 5 failed, 8 skipped. Not resolved here. Acceptance: whoever audits W7.0a reruns that test with the key present or explains the dependency.

**F8. Materialized copies have no durable custody record.** Severity: medium. Confidence: high. Files: `src/adrl/ledger/capture.py:398-430`, `src/adrl/ledger/session_verification.py:269`. Claim: matches the author's own gap statement. Consequence: real payload capture is correctly blocked; the packet W3.2b2e is the right next custody step for bulk or isolated collection. Acceptance: a lease table or marker directory with a startup reconciler and a test that a simulated kill leaves a reconcilable record.
