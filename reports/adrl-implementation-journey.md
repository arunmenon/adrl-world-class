## 2026-09-08, entry 004: A close request now has a durable history

**What changed:** W3.2a adds an internal encrypted attempt journal. It preserves a task's initial
included-tree manifest, reserves distinct attempt/future capture IDs and records close requests,
cancellation and explicit interruption as later events. Resending the original start after
editing the folder returns the original starting point. Changed commands conflict instead of
replacing it.

The journal admits one active attempt per canonical workspace across sessions on the same
ledger. The check and append share a serialized database transaction. On restart, a pending
close remains pending. An identical request still retrieves its original acknowledgement after
later phases or a lost acknowledgement. A missing start, sequence gap or corrupt event prevents
a valid history from being returned.

**What this means in plain language:** ADRL can now remember “we started here,” “someone asked to
finish,” and “this was interrupted” without treating those statements as “the code succeeded.”
That distinction protects the future evidence used for course correction. This component records
intent; it does not supervise processes or associate a retained capture with the close request.
Those are W3.2b's next responsibilities.

**Evidence:** all **631 tests and eleven engineering checks pass**, with no declared-source drift.
Thirty-seven new journal cases and one migration case were added. They cover concurrent starts,
request/parent conflicts, ordering, pending restart, identity/expiry/erasure, restored keys,

read after the new migration, and earlier verification receipts still decrypt. The inventory
now accounts for **273 fields**. No real task payload, model call, paid usage or routing change

## 2026-09-08, entry 005: Own the process before claiming it finished

**What changed:** W3.2b1 adds an internal runner for one bounded synthetic command at a time.
A private launcher owns its process group, reports the direct command's exit and stays alive
through cleanup. ADRL sends its final group signal before reaping that launcher. It never
signals the group after releasing its identity, and has no saved-PID restore/attach API.

The launcher reacts to owner-pipe closure and a watchdog. The runner handles timeout, explicit
stop, repeated coroutine cancellation and event-loop shutdown. A failed signal or unconfirmed
reap prevents reuse of that runner. Inputs and executable digests are checked; children receive
only the minimal documented environment plus explicit operator values, and no control
descriptors. Output is discarded. In-memory reports preserve separate exit/cleanup observations,
policy and source identities and keyed request provenance without raw task material.

**Why this matters:** a task can say it finished while a helper is still writing. Judging a
snapshot taken at that point could give our improvement loop the wrong answer. This slice
builds part of the ownership and cleanup machinery needed to avoid that mistake. It is not
yet connected to the attempt journal, capture archive or verifier.

**What the tests taught us:** same-group cleanup handles the tested lingering helper. A
deliberately detached child survives and performs its bounded write. That is an observed
limitation, not a waived failure. Every result says its scope is only the process group and
sets exact-close and learning eligibility to false. Unrelated editors and outstanding kernel
work are also outside the established boundary. This is not a hostile-code sandbox.

**Evidence:** all **669 tests and eleven checks pass**, with 38 new process cases and no
declared-source drift. Tests include exits, lingering/detached children, timeout, stops,

**Corrections:** lint probes found async fixture operations, long lines and a missing retained

## 2026-09-08, entry 007: A recovery failure changed the next step

**What we found:** while preparing process/erasure coordination, we found that the keystore
removed its wrapped key before recording the shred audit. A disposable fault probe forced
that audit to fail. Restoring the saved wrapped file made the old key readable; deleting
it then allowed a new key for the same session. This contradicted the intended no-resurrection
behavior. No actual user key or payload was used.

**Course correction:** we split out W3.2b2b1 to repair that prerequisite before connecting
more machinery to erasure. ADRL now persists a private revocation marker, flushes it and its
directory, and only then mutates the key file. Key reads, presence checks and creation honor
the marker even when deletion/audit fails or an old file is restored. Legacy audit records
also deny restored keys when the attached ledger is available. The marker has no removal API.

**Supporting changes:** cooperating keystore readers/writers use a private nonblocking POSIX
lock. It is released before ledger audit waits. Key writes are private atomic replacements;
known pending files from interrupted writes are cleaned by their owning session's create/shred
or by host-secret initialization. Unsafe identities, aliases and special files are rejected.
Product access recognizes revocation after audit failure: the timeline keeps its payload
unavailable and rebinding/event submission remain forbidden.

**Evidence:** all **724 tests and eleven checks pass** with no declared-source drift. There
are 26 new revocation cases and one product integration case. They cover audit/removal/marker
failure, restart, a real process death after revocation, missing/corrupt/restored keys, legacy
audits, contention, lock/audit ordering, unsafe files and owned pending copies. The first new
suite passed 23 cases; expanded revocation/product coverage passed all 80. The first full
combined run passed. Lint findings were corrected; no behavior test failed or invariant was
waived. The pre-change failure probe remains in the evidence record.

metadata entries documented. Temporary host-secret and wrapped-key files are explicitly key
material. Database schema 9 and public API preview 4 are unchanged. No model-service call,

**Limits:** a marker can deny future access through current APIs; it cannot withdraw cached
keys or plaintext. Physical blocks, snapshots, backups, whole-keystore rollback, older binaries

errors; the product's erased payload state indicates access denial, not certified physical

## 2026-09-08, entry 008: Closing a job ticket cannot release a workspace

**What changed:** W3.2b2b2 connects a readable v2 attempt and its terminal quota grant to the
owned process-group runner. It commits a separate durable workspace block before launch.
Another coordinator or a new journal start cannot reuse that workspace after cancellation,
